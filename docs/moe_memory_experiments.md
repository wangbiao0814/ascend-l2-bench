# 910C MoE 访存瓶颈验证方案

状态：基础实验代码已按本方案落地，运行方式与尚未覆盖的部分见 [运行说明](moe_experiments_runbook.md)。已做 CPU 模拟验证，尚未完成 CANN/910C 编译与上板采样；没有新硬件实测结果。

研究对象：用户提供页面的三项假设——权重读取串行、专家权重在复用前被淘汰、KV 散读阻塞关键读取。
用户已确认“加载”指 **NPU HBM → 片上缓存/计算单元**，不是 CPU → NPU 搬运。
目标环境：910C、CANN 9.0.0；当前 benchmark 报告可用 AIV 核为 48。不能由 AIV 数推断 Cube 数或跨 stream 并发能力。

## 1. 结论等级与现有证据

页面上的 35–44 μs、106–132 μs、57 μs 和 1→0.25 TB/s 是待复核的原页面观测，不是本机实验的目标答案或已验证事实。专家/层的字节数、精度、参与核数、batch 和采集口径必须一致，才可比较这些数字。

| 假设 | 最低有效证据 | 只看耗时不能证明什么 |
|---|---|---|
| H1：关键权重读取有可隐藏的串行等待 | 实际并发时间线 + 提前读取降低后续等待 + 整段完成时间下降 | 提前读完不代表数据驻留；增加一遍读取不一定有净收益 |
| H2：专家 A 在再次使用前被其他工作逐出缓存 | 同地址第二次 A 的读取变慢，同时 A 的主存读取量增加；调度复用可逆转 | 不能由 A→B→A 的耗时直接算 L2 容量，也不能说 HBM 中的权重被释放 |
| H3a：散读干扰关键读取 | 在确实重叠执行时，关键请求 p50/p95 升高，限制背景并发能够恢复 | 不能区分带宽、缓存、TLB、MTE 或请求资源争用 |
| H3b：请求槽/返回缓冲资源是具体限制 | 同等实际内存流量下对请求粒度/并发度敏感，排除主要替代解释，最好有对应停顿/占用计数器 | 没有可用硬件计数器时，只能报告“与请求资源争用一致”，不能报告“请求槽已满” |

现有 benchmark：一次启动内的相同 tile 重用可观察到明显差异；repeats=1 时 group 近似等效；L2 请求开关几乎没有造成差异。这些结果不能直接验证 H1/H3，也不足以确定 H2 的原因。

## 2. 通用实验条件

### 2.1 等价工作负载

- 保持无 PyTorch 依赖：原生 CANN/ACL Host + Ascend C 访存探针；Python 标准库组织实验与结果。
- 原始权重全部事先放在 HBM，分配、初始化、格式转换、随机数生成、正确性检查均不在目标计时区间内。
- 每次专家调用内部只遍历权重一次（repeats=1）。复用发生在两个独立调用/两个 microbatch 之间。
- 同一试验的所有策略使用相同物理缓冲、权重地址、token→expert 路由与有用计算；只改变明确研究的调度或背景请求模式。
- 不再把每个权重元素加一并写回等大输出。增加只读为主的探针：读完每个 tile 后做可验证的校验和，最终每核只写一份小结果。校验依赖全部输入，检查编译产物，防止访问被优化掉。
- 校验和探针不是专家 GEMM：先量化其额外计算成本，再以真实 BF16/INT8 专家计算复核。不能把同字节数的 FP32 扫描解释为真实 INT8 专家性能。
- INT8 的量化 scale、解量化和 gate/up/down 三个矩阵分别统计；先做单矩阵，再做完整专家，避免总权重尺寸与一次 kernel 的活跃尺寸混淆。

### 2.2 建议扫描范围（均为设计参数，不是已测硬件容量）

| 参数 | 起始范围 |
|---|---|
| 单块权重字节数 | 4、8、16、28、32、42、56、64、84、96、128、168 MiB |
| 初始基线 | 16 KiB tile、repeats=1、显式记录实际 AIV 核数 |
| 访存探针核数 | 1、4、12、24、48；读 H1 并发时另扫小规模预取核数 |
| 专家计算 token 数 M | 1、8、32、128；先用目标模型真实矩阵形状 |
| 独立专家数 | 1、2、4、8；按路由序列定义，非 kernel 内 repeats |
| KV 请求有效块大小 | 256 B、1 KiB、4 KiB、16 KiB；均满足所选接口的对齐约束 |

每次先查询 UB、可用核及运行时能力，超出能力的组合不运行。不要默认支持 cache pin、物理核亲和或硬件请求槽预留。

### 2.3 统计与计时

- 短任务用设备事件和系统级任务时间线交叉核对，记录微秒且保留至少 3 位小数；不要从日志里四舍五入后的 ms 反算差值。
- 先完成设备频率预热，再执行每次试验的显式 cache 前缀；频率预热不等于把目标权重预热。
- 最少 30 个独立试验区组；组内以固定随机种子打乱对照顺序。保存每次原始数据，报告 p50、p95 与配对差值的 95% 置信区间。
- 空 kernel、单 stream 串行任务、无访存但同样索引/控制逻辑分别作为启动和调度基线。
- 主结论使用无 profiler 延迟；采样轮次用于解释。多计数器可能重放，不能混用重放时间与无 profiler 时间。
- 全部模式验证输出及访问覆盖。索引读取要把重排结果恢复到原 token 顺序后再比对。

## 3. E0：先建立可信的冷、热读取基线

目的：明确可复用窗口，并检查 L2 hint 是否真的改变硬件行为。

对同一缓冲 A 执行三种前缀，然后计时一次相同的 read_probe(A)：

1. **热读取**：先 read_probe(A)，随后立即计时 read_probe(A)。
2. **干扰后读取**：先 read_probe(A)，再遍历独立缓冲 D，随后计时 read_probe(A)。
3. **未立即复用的地址**：从预分配权重池中选择当前区组未刚访问的等大缓冲；初始化完成后先执行统一前缀，不能把初始化后的首次读取直接称为冷缓存。

D 从 0、16、32、64、128、256、512、1024 MiB 起扫，必要时增加；驱逐遍历不计入目标 A 时间，但资源/成本另记。没有硬件 flush 时称为“干扰前缀/尽力驱逐”，不能保证全冷。

每组分别尝试 NORMAL/DISABLE，并检查生成指令及 L2、主存读流量。若这两个模式仍无可验证的流量差异，后续将其仅作为请求策略标签，不用它们给冷热状态下定义。

**准入条件**：至少找到可重复的热、干扰差异，或记录该尺寸下未找到可复用收益。没有 E0 的正控制，E1 的缓存预读和 E2 的淘汰结论可能不可识别。

## 4. E1：权重是否存在可隐藏的串行等待

### 4.1 任务定义与时间线

- C0：前一段已可执行的计算，主实验使用真实 GEMM/目标模型前序计算。
- P1：读取下一专家 W1 的预读探针，读到片上但不能保证驻留到 G1。
- G1：真正使用 W1 的下一段 GEMM/专家计算，输入依赖 C0；W1 地址已提前确定。
- 如果路由依赖 C0 完成后才能获得，必须另外记录 route_ready；P1 不能在地址未知时凭空提前。已知路由使用 oracle 模式，实际路由就绪使用 deployable 模式，分别报告。

比较三个必要对照：

```text
D0 实际按需基线：C0 ----------------→ G1（正常按需读取 W1）
D1 串行预读对照：C0 ----------------→ P1 → G1
D2 提前预读：    C0 ----------------→ 等待必要依赖 → G1
                    P1 -----------→ 完成事件
```

D1/D2 执行完全相同的 C0/P1/G1，只改变 P1 的发起时机。D0 不做额外预读，用于判断优化是否值得。仅比 D2 与 D1 可能高估实际可获收益，因为 D1 人为多加了一遍串行预读。

### 4.2 实施与控制

- 两个 ACL stream，明确 ready 事件；G1 同时依赖 C0 和 P1 的完成事件。提交期间不做每个 kernel 后的 host 同步，末尾统一汇合计时。
- 时间线必须显示 C0 与 P1 确实重叠。两个 stream 不自动等于设备并发；若硬件/资源使其串行，记录“并发条件未满足”。
- 分别测试计算占主导的 C0 与访存占主导的 C0；后者是预取争用 HBM 的负对照。
- 预取块数/核数从 1、4、8、12 起扫，逐步增加；目标是提高整段收益，不是最大化预读带宽。
- 扫权重尺寸、C0 计算窗口与提前量。C0 窗口先覆盖实测 P1 耗时的约 0.5、1、2 倍，观察不足/适中/过早预取。
- 不跨 kernel 保留 UB 内容，也不假设下一 kernel 会在同一个核上执行。若做软件 UB/L1 常驻，只能作为另一个融合 kernel 实验，不能称为跨 kernel L2 预取。

### 4.3 记录与判据

记录 C0/G1/P1 的开始结束、路由就绪、G1 可执行后到首次有效计算的等待（若时间线可观测）、整段 makespan、C0 变慢量、W1 主存读取字节数。

```text
调度移动收益 = T(D1) - T(D2)
实际净收益   = T(D0) - T(D2)
```

- D2 的重叠存在，后续 G1 的访存等待减少，且实际净收益的置信区间大于零：支持该配置存在可隐藏的关键读取等待。
- 只见 G1 变快、整段不变：只能说等待被转移或争用抵消，不能说端到端优化成功。
- D2 比 D1 快、却不如 D0：额外预读代价过高，不能支持该预读方案的实际价值。
- P1 结束后 G1 没有变快：检查缓存驻留、路由可提前性、G1 是否计算受限，不能直接断言“无串行瓶颈”。

## 5. E2：同专家在两次使用间是否被淘汰

### 5.1 固定工作集合的顺序对照

创建互不别名的权重 A、B、C。A1、A2 表示同一地址的 A 被两批 token 使用，均是单次完整调用。

```text
I0 交错：A1 → B → C → A2
I1 聚集：A1 → A2 → B → C
```

两组必须执行相同的两次 A、一次 B、一次 C，保持 token 数、权重地址和校验结果一致。分别计时 A2 和整段。没有 token 依赖时才可重排；有依赖时先把它作为 oracle 上界，再做合法的调度窗口。

为单独区分“容量干扰”和“仅隔得久”，加入相同 A 前后缀：

```text
C0：A1 → A2
C1：A1 → 只计算、不遍历大缓冲 → A2
C2：A1 → 读取独立 D             → A2
```

C1 的间隔校准到接近 C2，用来排除单纯时间、频率和任务间隙；不是用 sleep 伪造 GPU 计算。

### 5.2 扫描

- 先用 A=16/28/42 MiB 做正控制，再做 56/84/168 MiB。
- 逐步增加 B/C/D 字节数及专家数量，另加入 KV 随机块读作为干扰类型。
- 给定字节数时保持 tile 和核数不变；之后再扫核数，检查工作集和核调度的影响。
- 先做纯读探针，再做真实专家 GEMM。后者分 gate/up/down 阶段观察，因为单矩阵及活跃 tile 比完整专家总尺寸更直接影响局部缓存。
- 不把 A1 的正常 demand 读取与 A2 的缓存复用称为“同一 kernel 读 8 次”。这是两个独立专家调用之间的复用。

### 5.3 判据

同时满足以下证据时，支持“复用前被淘汰，导致额外 HBM 加载”：

1. E0 表明该尺寸 A 立即重用时确有收益。
2. I0/C2 中 A2 的延迟上升，而且 A2 的主存读字节量上升、L2 读命中下降（如指标可用）。
3. 相同的时间间隔、仅计算的 C1 不产生同等程度退化。
4. 聚集 I1 可降低 A2 的读取量/延迟，整段时间也下降。

只看到延迟变化而没有读取流量证据：结论限定为“跨调用局部性收益/干扰效应”，不声称已经定位到 L2 淘汰。

“保护”的首个干预是缩短复用间隔、限制穿插的干扰工作。不得把预分配 HBM、NORMAL hint 或减少其他 stream 等同于硬件 cache pin，也不假设支持 L2 持久驻留。

## 6. E3：KV 散读是否阻塞关键读取，能否归因于请求资源

### 6.1 工作负载

- 前景 F：固定地址集合、固定字节数和核数的关键读取；权重读取可用 28/42 MiB 探针，短延迟探针可用 64 KiB/1 MiB。冷热状态分别建组。
- 背景 K：独立 KV 池，建议从 512 MiB/2 GiB 池扫描；固定有用读取字节数及索引集合，改变每请求块大小、顺序和可并行的块数。
- K 的索引由预生成数组给出。顺序/随机对照读取同一地址多重集合，避免“随机模式实际读了更多数据”。记录索引读流量，另做仅索引、无 KV 载荷的控制。
- 控制大页/普通页和按页聚集访问，区分 TLB、地址映射、cache line 放大与请求资源的作用。无法控制的映射因素明确列为限制。

### 6.2 必需对照矩阵

| 编号 | 运行方式 | 用途 |
|---|---|---|
| K0 | F 单独执行 | 前景基线 |
| K1 | K 单独执行 | 背景吞吐/时长基线 |
| K2 | F 与连续大块 K 实际重叠 | 带宽竞争对照 |
| K3 | F 与小块随机 K 实际重叠 | 散读 + 并发干扰 |
| K4 | K3 限制背景并行块数或发起节奏 | 检查准入控制是否降低前景排队 |
| K5 | 与 K3 类似的核/索引控制工作，但无大规模 KV 载荷 | 排查核调度/索引计算因素 |

第一轮：同样有用字节数，比较 K2/K3 的应用干扰。
第二轮：根据实际 HBM 读写流量/吞吐校准发起节奏，比较平均主存带宽相近的 K2/K3；不能只用“有用字节数相同”冒充“物理带宽占用相同”。

同一平均吞吐也不排除瞬时突发，需报告背景请求分布和时间窗中的流量。没有细粒度流量或请求占用观测时，保留替代解释。

### 6.3 并发与调度约束

- 扫 K 的 block 数/软件并行窗口（如 1、4、8、16）和请求块大小。这些是软件压力旋钮，不是硬件请求槽数量。
- 首先证明两个 stream 在设备上真实重叠，F 不是仅在 K 完成后才被调度。
- blockDim 变小不保证物理核预留。若没有可靠并发，可另设计单个混合 kernel 的前景/背景角色，以排除跨 kernel 调度排队；该版本与双 stream 版本分别报告，不能混称真实模型并发。
- 不引入未经验证的 stream 优先级保证或硬件槽位预留 API。K4 是限制背景发起数量/节奏的“软件准入控制”。
- 所有 K0–K4 的前景操作保持相同；记录完整背景完成时间与整段 makespan，防止靠无限延后 KV 获得虚假的优化。

### 6.4 记录与结论

记录 F 的提交/设备开始/完成时间、p50/p95、K 完成时间、有用带宽、实际主存带宽、L2、MTE 管线与可用停顿指标。

```text
前景干扰代价 = latency(F | K) - latency(F alone)
准入控制收益 = latency(F | K3) - latency(F | K4)
代价         = completion(K4) - completion(K3)
```

- K3 明显慢于 K0：散读存在干扰，不足以认定槽满。
- K3 相比物理带宽相近的 K2 产生更高前景尾延迟，且随软件并行窗口增加出现拐点、K4 可恢复：与请求资源/延迟压力一致。
- 若 L2 miss/主存流量显著变化，优先考虑 cache 污染；若 F 的设备开始明显延后，优先考虑 kernel 调度；若已达相同流式带宽平台，优先考虑带宽竞争。
- 只有目标版本/产品确实暴露并采集到了对应请求资源占用或停顿证据，才可进一步报告“请求槽/返回缓冲受限”。不要把 ResourceConflictRatio 这样的通用指标直接当作请求槽满计数器。
- 没有可用底层指标时，结论上限是 H3a 及 H3b 的间接证据；明确无法直接确认槽位数或满占用。

## 7. 设计时接口草案（当前实现以 csrc/probe_api.h 为准）

这是一组实验 harness 与原生访存探针，不对应现成 PyTorch/NumPy 同名算子，不新增框架适配。

```cpp
struct ReadProbeSpec {
    uint64_t bytes;          // 实际完整读取字节数
    uint32_t tileBytes;      // 默认 16384，可扫描
    uint32_t blockDim;       // 不超过设备可用 AIV 核数
    uint32_t cachePolicy;    // 请求值；另行核实实际行为
};
struct KvProbeSpec {
    uint64_t poolBytes;
    uint64_t usefulBytes;
    uint32_t chunkBytes;
    uint32_t blockDim;
    uint32_t softwareWindow; // 不等同物理槽数
    uint32_t seed;
};
// 原生 C ABI，沿用项目错误返回形式；stream 由异步实验 session 管理。
int read_probe_async(void *session, void *stream, const void *weight,
                     void *checksum, const ReadProbeSpec *spec);
int kv_probe_async(void *session, void *stream, const void *pool,
                   const void *indices, void *checksum, const KvProbeSpec *spec);
```

### 7.1 Ascend C 路径与分核

访存探针采用 Ascend C；真实 GEMM 首先调用可用 ACLNN 算子，若必须精确控制分块再另做 CATLASS/融合版本。

- read_probe：沿用轮转 tile 分配，tile `t` 归核 `t % blockDim`。所有有效 tile 恰读一次，不重叠写 checksum。
- kv_probe：按请求编号轮转分核，以预生成索引确定 GM 地址。每次搬移同一有效块，尾块由长度显式限定，不能为了对齐多读而不计流量。
- 内存访问基线先使用 FP32 合成数值做校验和，读取字节数与权重目标相同；INT8/BF16 版本需按目标 API 支持矩阵确认转换路径后实现，不假设任意 Cast 都可直达。

```text
read_probe（FP32 基线）:
  for t = blockIdx; t < totalTiles; t += blockDim:
    input = inQueue.AllocTensor<float>()
    DataCopyPad(input, GM[t], 实际有效字节数)
    inQueue.EnQue(input)
    input = inQueue.DeQue<float>()
    ReduceSum(tileSum, input, reduceScratch, 有效元素数)
    Add(coreAccumulator, coreAccumulator, tileSum, 对齐后的标量缓冲)
    inQueue.FreeTensor(input)
  DataCopyPad(checksum[blockIdx], coreAccumulator, 有效结果字节数)

kv_probe:
  按请求编号分核；读取 indices 得到 GM 块偏移
  对每个有效块执行同样 CopyIn → 校验和 → 释放
  softwareWindow>1 时用有界队列流水，验证真实重叠而非只增加缓冲数量
```

### 7.2 UB 与 workspace 规划

默认 16 KiB 读取 tile；不生成等大输出队列。ReduceSum 的具体临时空间以所选 API 的官方最小/最大临时空间查询为准。

| 资源 | 规划字节数 |
|---|---:|
| 双缓冲输入队列 | `2 * tileBytes`，默认 32 KiB |
| 归约临时空间 | `reduceScratchBytes`，实现阶段查询，不填猜测常数 |
| tileSum + coreAccumulator | 至少各 32 B，视所用 API 对齐要求调整 |
| KV 索引缓存 | `align32(indexBatch * indexElementBytes)` |
| INT8/BF16 转换缓冲 | 仅对应版本需要；按转换路径逐项计入 |

总 UB 使用量 = 上表实际启用资源之和，必须小于查询到的 UB 容量减预留空间。softwareWindow 扩大时同步检查缓冲和队列上限。Host 自动缩小 tile 或拒绝超限组合。

GM workspace：每核独立 checksum、预生成索引，以及所选 GEMM API 查询得到的 workspace。独立访存探针不因“逐元素”而固定申请 16 MiB 系统 workspace。Host/C ABI 标量参数无需额外 tiling GM buffer。

### 7.3 现有工程必须改动的边界

- 保留原 bench.py 作为历史基线，不把它的输出含义悄悄换成专家延迟。
- 增加独立实验入口与原生 read/kv 探针，分开保存结果。
- 当前 `l2_run` 每次启动后同步 stream；E1/E3 不能直接复用该同步方式。新增 enqueue-only 和最终 synchronize/event join 接口，不把“两个同步调用”误当并发。
- 沿用现有 CANN 构建入口，不引入 torch、torch_npu 或 wheel 打包。
- 保存每个阶段 launch_id、expert_id、microbatch_id、stream_id 与事件依赖；不能只输出整个程序一个耗时。

## 8. 采集方式与结果字段

1. 无 profiler：设备事件、整段完成时间、正确性、原始 trial 数据。
2. 系统时间线：检查 C0/P1/G1 或 F/K 的真实重叠、任务调度延迟、等待位置。
3. 单算子计数器：在支持时采集 L2Cache、Memory、PipeUtilization；ResourceConflictRatio 仅按其真实定义解释。
4. E1/E2 涉及跨 kernel 的缓存历史，不使用会清空 L2 的 kernel/range replay 来替代原序列。若已安装版本支持 application replay，则每轮重建完整初始化与前缀、按 launch_id 选中目标，并确认 replay 保留研究所需的历史。
5. E3 并发关系不能被计数器采集过程串行化；若工具不支持保留并发，用无 profiler 时间线为主，并明确计数器只能提供单任务校准。
6. 具体参数取本机 CANN 9.0.0 的帮助输出，不直接照搬最新版工具命令。指标缺失时保留 NA，不用估算值填充。

建议结果字段：

```text
experiment, variant, trial, seed, device, soc, cann_version,
weight_bytes, matrix_shape, dtype, tokens, expert_id, microbatch_id,
tile_bytes, blocks, kv_pool_bytes, kv_chunk_bytes, kv_useful_bytes,
software_window, stream_id, launch_id,
route_ready_us, device_start_us, device_end_us, duration_us, makespan_us,
hbm_read_bytes, hbm_write_bytes, l2_read_hit_rate,
metrics_available, concurrency_verified, correctness_passed
```

不能把逻辑字节数写入 hbm_read_bytes；设备计数器只有比例/速率时按原指标保存，不能无依据反推归属于某一阶段的流量。跨 stream 时间戳必须使用同一可比较设备时基；仅主机提交时间不能代替设备开始时间。

## 9. 最小实施顺序与验收

1. **E0 + read_probe**：去掉等大输出写，确认热/干扰状态与 cache hint 行为。
2. **E2**：同一专家的跨调用复用与干扰对照；这一步最接近现有 L2 实验。
3. **E1**：新增真正异步 Host，验证串行等待与预读净收益。
4. **E3**：新增 KV 随机块探针，先证明干扰，再判断能否归因到请求资源。
5. 选小矩阵/合成负载通过后，再换真实 MoE 专家和实际合法路由调度。

验收检查：

- [ ] 读探针全输入依赖、校验正确、每次调用只读一遍。
- [ ] 权重及 KV 地址集合/读取字节数在成对对照中一致。
- [ ] 各试验起始 cache 状态与重放方式可追溯。
- [ ] E1/E3 有实际并发的正证据；失败时区分能力限制与负结果。
- [ ] E2 有即时重用的正控制，才能讨论“被淘汰”。
- [ ] 核心结论有独立 trial、原始数据及不确定性，不使用页面数字作为通过阈值。
- [ ] 报告整段净收益和后台代价，不仅报告被优化阶段。
- [ ] 无法观测请求槽时不声称已经直接证明槽满。
